# Agent control and live project edits

Conductor exposes a first-party internal JSON protocol over an ephemeral loopback HTTP port. This implements feature 17 without changing the provider MCP policy. The server belongs to the app; there are no per-tab MCP processes or third-party configuration changes.

The first prompt of each native runtime receives a short briefing with the endpoint, a random per-conversation bearer credential, and `tools.list` discovery; it is sent again after a resume, a reconnect or a context compaction, never on every turn (see `docs/context-accounting.md`). Requests are `POST /control`, `Content-Type: application/json`, `Authorization: Bearer <credential>`, with a body of `{ "method": "tabs.list", "args": {} }`. Replies contain either `result` or `error`. Never print credentials in reports or blindly retry a mutation after a timeout. The briefing directs agents to use visible Conductor tabs when delegating to another provider.

The authority is the registered native conversation, its project, and its active workspace. An agent cannot substitute another project or workspace, operate on a hidden session, or control itself or any ancestor. Persistent parent relationships use the existing settings store, so busy collaboration logs cannot erase cycle protection. Collaboration handoff messages provide the audit trail. A human can release a relationship from the visible connection strip. Destructive tab closure and forgetting an agent memory require a native owner confirmation dialog; a request argument cannot grant approval. Human-authored memories cannot be forgotten or merged into by agent writes.

The endpoint binds only to `127.0.0.1`, checks its exact Host header, rejects browser Origin requests, accepts only authenticated JSON POSTs, and limits bodies to 3 MiB. Each credential may hold at most eight in-flight requests (a ninth receives `429`). Read-only and waiting methods — discovery/list/status reads, agent snapshots/history/artifacts, files reads, usage limits, repository/update status, and durable-job reads — run concurrently, including while a mutation is in flight. Mutations are serialized in arrival order per credential and method family (delivery, tabs/router, agents, app lifecycle, files/tasks/memory, jobs/schedules/loops, and the rest; `src/main/control-method-classes.ts`), so one caller cannot race its own state changes within a family, and a long `git.ship` never holds up that caller's `tabs.open`. Closing a workspace/tab revokes its authority; moving saved history to a different workspace rotates its credential. History moves preserve the native session ID and permission settings and cannot cross projects or steal a conversation still open elsewhere. App control is disabled entirely in the explicitly isolated live acceptance suite. Codex's existing third-party MCP isolation and Claude's configuration policy remain unchanged.

## The `control` MCP tool

Claude and Codex tabs get the `conductor` MCP server (`src/main/permission-grants/control-mcp.ts`), and its `control({method, args})` tool is the first way to call app control: `control({method:"tools.list", args:{brief:true}})`, `control({method:"agents.status", args:{agentSessionId:"agent_..."}})`. It runs as the calling conversation through the HTTP endpoint's own pipeline (`AgentControlServer.invoke`: the same credential scope, owner-only and destructive rules, in-flight cap, per-family mutation order and timeline activity), so nothing is quoted in a shell and no token reaches a command line, where the auto-mode classifier reads it as a bypass. A refusal comes back as `isError` with exactly the text HTTP answers in its `400` body; `args` sent as a JSON string is accepted. An approval reviewer's session rule for it covers one method (`mcp:mcp__conductor__control:<method>`), never the whole tool. `send_message`, `report`, `submit_task` and `handoff` stay the normal way to message tabs. The HTTP protocol below remains for scripts and for providers without the MCP server.

## Reading a refusal

Prefer the conductor `control` tool when you have it. From a shell use `curl.exe -s`: a refused call is HTTP `400` whose JSON body `{"error":"..."}` says what to do next, and Windows PowerShell's `Invoke-RestMethod` throws "(400) Bad Request" and hides that body unless you catch it: `try { Invoke-RestMethod ... } catch { $_.ErrorDetails.Message }` (`-SkipHttpErrorCheck` does not exist in PowerShell 5.1). Read the error before retrying; it names the missing argument, the other party or the call to make instead. `401` is a revoked or wrong credential (the text says to use the conductor MCP tools, or to say so in the final message so the owner restarts the conversation), `429` too many calls in flight from one conversation (wait for one to answer; never resend a mutation that timed out without checking `agents.list` or `git.ship.status` first), `403` a request that is not a local JSON POST.

Every refusal ends with the next step (H15, 2026-09-28; the conventions below are what to expect, so do not guess around them):

- **Arguments** (`src/main/control-args.ts`). A method with a fixed argument list refuses anything else by name: `<method> accepts only <list>; <extra> is not an argument (did you mean <key>?).` An argument refusal is prefixed with the method (`agents.report: text is required`). Keys that mean one thing unambiguously are accepted as aliases: `agentId` or `tabId` for `agentSessionId` on every `agents.*` method that names one conversation; `taskId` for `id` on `orchestration.tasks.update`; `id`/`scheduleId` for `taskId` on `schedules.*`; `message`/`report`/`summary`/`content` for `text` on `agents.report`; `id`/`outputArtifactId` for `artifactId` on `agents.artifact`; `after`/`since` for `afterSequence` and `beforeSequence` for `before` on `agents.history`; `commitMessage` for `message`, `files` for `paths` and `wait` for `waitSeconds` on `git.ship` (`id` for `runId` and `wait`/`timeoutSeconds` for `waitSeconds` on `git.ship.status`); `wait` for `waitSeconds` on `agents.finish`. An alias and its key given with different values are refused.
- **Unknown methods**: `Unknown control method "<name>" in build <version>. Did you mean <closest>? tools.list({prefix:"<family>."}) lists that family; if the method is newer than this build, app.update installs the checkout's build.` The suggestion comes from a map of names agents reach for (`agents.send|message|reply → agents.steer`, `git.commit|push → git.ship`, `tabs.create|agents.open|start → tabs.open`, `agents.close|done → agents.finish`, `agents.get → agents.status`, ...) and otherwise the nearest method within three edits. It is only suggested, never run. The conductor MCP server answers an unknown tool the same way, listing its tools.
- **Read-only or planning**: one text for every write: `This conversation is read-only or planning, so <method> was refused. The owner can switch this tab out of plan/read-only in its composer; otherwise hand the change to a writable coworker (tabs.open) or report what should be done (agents.report).`
- **Conflicts name the other party**: a tab another controller holds (`"<tab>" is controlled by "<title>" (<id>); send_message that controller, or ask it to agents.release the tab`), a cross-project tab likewise, an edit lease (`"<title>" (<id>) holds an edit lease on <path> until <time>`), a claimed checklist task (`tasks.update`) and each `router.dispatch` `projectTaskIds` entry (missing, already done, or claimed by whom).
- **A tab closed mid-turn**: `This conversation's tab was closed while its turn was running, so Conductor accepts no control calls from it ... End this turn with your result as your final message: the paths you changed, the commit message you meant to ship and what you verified; your controller or the owner reads it with agents.history.` The one exception (owner decision, 2026-09-28) is `agents.report`, still delivered while a control link names the caller's controller (the live link, or the one kept when it finished; a superseded controller's successor receives it), so finished work is not stranded. `git.ship` stays refused: hand the paths and commit message to the controller.

Model ids resolve from what callers actually write (`resolveModel`, `src/main/control-args.ts`): the exact id, then the same id in another case, then its 1M-context form (`opus` → `opus[1m]`), then a label written out in full, then the one model whose id (else label) contains the name (`fable` → `claude-fable-5-1`, `astra` → `gpt-6-astra`). Several candidates at the last step are refused, not guessed. `tabs.open`, `router.dispatch`, `agents.configure`, `agents.handoff` and `jobs.create` use it, and a result opened on a resolved id says `modelResolvedFrom: "<what was asked>"`. A model of another provider is refused with `"gpt-6-astra" is a codex model; pass provider:"codex" (you asked for claude).`, an unknown one with every id the provider offers, and an unavailable provider with the available ones. `router.dispatch` checks provider, model, effort and permission of every task before it opens any tab (`Task 2 ("<title>"): <error>; no task was opened.`), and a task that fails later comes back `{title, accepted:false, error}` without undoing the tabs already opened. The names people use map to these ids:

## Tool surface

`tools.list()` returns signatures on demand, avoiding a large repeated tool catalog in every prompt. With no arguments it is the whole catalog (tens of KB); `tools.list({brief:true})` names every method with its arguments only, and `tools.list({prefix:"agents."})` or `tools.list({methods:["git.ship"]})` gives the full text of just those.

| Tool output | `agents.artifact({agentSessionId,artifactId})` returns the full text of a tool output whose history event only carries a tail (`outputArtifactId`), or of a report longer than 2,000 characters, up to 2 MiB. |

Cross-project work goes through the target project's wizard. `projects.list` names each project's active wizards (`wizards`: `agentSessionId`, `title`, `workspaceId`, `workspaceName`, `phase`; a wand tab on a frontier model, `wizardActive`), because that tab owns delivery, coordination and the shared working tree of its project. A `tabs.open` or `router.dispatch` task with another project's `projectId`, or `agents.steer`/`agents.submit({projectId,prompt})` with no `agentSessionId` (the `send_message`/`submit_task` MCP tools with `projectId`), opens no tab when that project has a wizard and the caller named neither `workspaceId` nor `direct: true`: the prompt (after the title, if one was given) is steered into the wizard as `agents.steer` would, prefixed `[From <caller title> (<caller agentSessionId>, project <name>)]`, and the result is `{deliveredTo: {agentSessionId, title, projectId, workspaceId}, delivery: "started"|"queued", note}`; a dispatch task delivered this way gets no orchestration row. The wizard never becomes the caller's coworker: a later `agents.steer`/`agents.submit` to it from another project is a message too, and the wizard may answer any conversation that handed it work (`send_message`, result `reply: true, controlled: false`) without taking it over. With no wizard, the tab opens in the workspace of that project's most recently active root controller (a conversation nobody controls that controls coworkers), else in its first workspace as before. `direct: true` keeps the old behavior for a caller that really wants its own tab; the owner credential and sandboxed local models are not routed. This came from 2026-09-28, when the Haftheme wizard opened a fixer in the Conductor project that Conductor's own wizard never heard about.

Stable links use `conductor://<project>/tab/<encoded-tab-id>`, `/file/<encoded-path>`, or `/workspace/<encoded-workspace-id>`. Clicking a conversation link resolves its exact registered resource and focuses the correct main or detached window. It does not search filenames or use an external browser.

Read-only permission, a read-only execution sandbox, or planning mode blocks file/checklist writes and dispatch into writable conversations. Newly opened coworkers inherit the restriction: Codex uses its read-only sandbox; Claude and Grok use their planning mode; a local model uses its read-only permission, under which the local runtime offers no write tool and no `run_command` (it has no execution-sandbox mode to name, so dispatch sets `sandbox: "read-only"` only for a provider that advertises it). Delegated turns retain the target conversation's existing settings and appear as normal user messages and native output in the visible tab.

## Router and real-time edits

The router is an `OrchestrationAgent` with role `conductor-router` and a persisted `RoutineDefinition` named `Conductor router`. Starting it creates a routine run and an in-progress task, opens a real native agent tab, and submits the user's work plus concise coordination instructions. The router reads the model catalog, chooses provider/model/effort for bounded tasks, and calls `router.dispatch`. Each coworker has a visible tab, native session, persistent orchestration agent/task, and a controller link. The assigned agents update completion through the same task API; dispatch failures mark their tasks blocked.

Feature 18 adds project directory watches plus immediate notifications from protocol writes. Directory watches survive atomic file replacements. Clean open editors adopt current disk bytes and retain their view position. Dirty editors preserve the owner's buffer and its original comparison baseline, show a conflict, and offer the existing save-copy/reload paths. The checklist refreshes from the same file-change notifications. Its periodic refresh remains a fallback.

## Validation

`src/main/agent-control.test.ts` covers project/workspace authorization, hidden/closed sessions, own/ancestor control denial, persisted links after more than 200 collaboration messages, owner confirmations, canonical path/junction escapes, competing file leases, stale writes, human memory ownership, task claims, plan/sandbox restrictions, history workspace relocation, credential rotation, request authentication/origins/size, isolated-live-test refusal, and a router run using the real stores and `StructuredSessions` with a synthetic provider boundary.

`scripts/smoke-agent-control.mjs` runs the real Electron main process, preload, renderer, loopback endpoint and router. By default its synthetic Claude source controls a visible Codex router and coworker. It checks native user/output events, persisted orchestration state, detached-window links and exact URI focus, live protocol/external atomic saves, dirty editor conflicts, and owner link release. Provider subprocesses are fixed offline fixtures; the test performs no model inference. Test-only captured briefing credentials are deleted on exit. Run after `npm.cmd run build`; the result is written to `artifacts/agent-control/report.json`.

`agents.handoff({handoff,title?})` is the one `agents.*` method that takes no `agentSessionId`: a conversation hands off only itself, because nobody outside it knows what its remaining work is and emptying a coworker's context from outside would be a way to erase it. It exists for the context-cost nudge described in `docs/token-thrift-policy.md`: past a band of its window, a conversation writes that document's bounded handoff — `Objective`, `Constraints`, `Owned files`, `Verified findings`, `Remaining work`, `Artifact references`, each heading on its own line and in that order, 200 to 12,000 characters — and calls this method. A handoff missing a section, or carrying them out of order, is refused by naming the section, because the receiver opens with no other context and cannot ask for it later. The new tab is opened through the ordinary `tabs.open` path in the caller's workspace, on the caller's provider, model, effort and permission, so the same clamping applies and a read-only or planning conversation hands off to a read-only or planning one — which is why it is allowed to hand off at all. The handoff is submitted through the ordinary `agents.submit` path, so the receiver gets the normal first-turn briefing and its own credential, and a `handoff` collaboration message from the caller names the tab that took the work over. The caller is never interrupted or closed: it keeps its tab, its history and its steering rights over what it opened, and the result tells it to finish the step it is in and stop rather than continue in parallel.

`agents.handoff({handoff, successor:true})` is main-brain succession: a wizard tab, or a controller with live coworkers, passes itself on to a fresh conversation that is the same brain rather than its coworker. Anyone else is refused and told to call it without `successor`. The receiver opens as a root (under the caller's own controller, if the caller had one, so a sub-controller's reports still go up), on the caller's model, effort and permission, and inherits wizard mode and limit continuation. Every live control link the caller holds, in any project, is rewritten to name the receiver in one synchronous step before its first prompt, so `agents.report`, approval review, steering, configuration and `app.update.authorize` clearances for those coworkers reach the successor, and the caller can no longer steer them. A pending restart initiator or `app.restart.request` naming the caller is re-pointed to the successor, so the next launch brings the successor back. The first prompt is the handoff followed by one Conductor line naming the predecessor and the coworkers taken over; it is submitted straight to the session, because `agents.submit` would link the receiver under the caller. Once it is accepted, the caller's wizard flag is cleared (one owner-authority main per workspace), it is marked superseded (`agents.supersede`, so nobody resumes it as unfinished work), and a Conductor notice in its timeline makes its tab read-only behind a "Continued in <tab>" banner with a button to the successor. If the successor refuses the prompt, the links and wizard flag are put back and the caller keeps working. Main brains are told when to do this: the per-runtime briefing (`src/main/turn-briefing.ts`) gives a wizard or controller one line, and Conductor posts a single notice in the tab when it passes 25 turns or 40% of its context.
