# Typing: long conversation and test load (2026-09-29)

Items: `typing-lag-long-conversation` and `typing-lag-under-test-load` (feature-list.md).
Targets:
- p95 under 16 ms on a 10k-event Claude conversation at 4x CPU throttle, at 1, 11 and 26 tabs.
- No p99 regression while a parked test instance starts, with a guard that fails when there is one.

## How it was measured

Every number comes from a parked, offline instance (`CONDUCTOR_TEST_USER_DATA`), measured on MAIN
(Ryzen 9 7900, 24 threads, RTX 5070). Other agents' builds, `tsc` and smokes ran on the machine the
whole time, and no llama-server was running (`local.servers` empty). Each run held the smoke lock
alone (`smoke-lock --priority normal`).

- Before is HEAD 2804a8e.
- After is that commit plus this change, built in a detached worktree. The shared `out/` holds other
  agents' unfinished edits, so it was not used.
- The composer change was delivered as 2892a5b. The guard's launch bound and these docs were
  delivered with this report.

The acceptance command is the one the overnight brief named, with a same-run floor added:

```
node scripts/smoke-lock.mjs --priority normal --timeout-min 45 -- node scripts/perf-input.mjs --provider=claude --events=10000 --tabs=1,11,26 --throttle=4 --floor --app=<build>/main/index.js
```

Each value is input-to-next-paint in ms: keydown, then the task after the next frame, over 300
keys, with the 10k conversation active (2,000 items, 60 rendered).

## 1. Typing into a long conversation

### What a key cost

A probe in the same parked window typed the same 300 keys into four things:
- the real composer;
- a bare `<textarea>` laid over the full app (`position: fixed; contain: strict`);
- a bare textarea with the app hidden;
- CSS variants of the composer.

That separated the composer's own cost from what the rest of the document costs each frame.
Values are per key at 4x, from CDP Performance metrics. The empty conversation was measured in
one launch; later rows are from the 10k conversation at 11 tabs.

| | p95 | task / key | script / key | React commits / 300 keys |
| --- | --- | --- | --- | --- |
| bare textarea, app hidden | 5.4–7.0 | – | – | – |
| bare textarea over the full app | 9.4–13.1 | 9.4–11.1 | 0.8–1.0 | 25 (periodic, not typing) |
| HEAD composer | 14.1–23.9 | 13.5–16.9 | 3.9–5.0 | ~325 |

HEAD's trace of the 10k conversation (`--trace --profile`) showed where the time went:

1. **The whole conversation pane rendered on every key.** `StructuredAgentPane` owned the draft's
   text. Each key re-rendered the pane: its header, the timeline wrapper (the timeline itself was
   memoized), the composer controls, the usage summary and about 150 lucide icons.
2. **React rewrote the controlled textarea on every render.** For a controlled `<textarea>`,
   React 19 writes `defaultValue`, which is the element's child text node, whenever it renders.
   Even after the pane stopped rendering, the textarea's own per-key render left script at
   5–6.5 ms per key (bare textarea: 1.0).
3. **A present placeholder costs a style recalc per key.** Blink rewrites the placeholder's inline
   style on every value change: 600 recalcs for 300 keys.

The rest was native frame work proportional to the document: text insertion with forced layout,
paint, layerize, and hit testing for the fake mouse move after layout. The bare textarea over the
full app pays that too.

### The fix

- **The textarea is uncontrolled** (`ComposerTextarea` in `StructuredAgentPane.tsx`,
  `useComposerTextSync` in `use-composer-draft.ts`). A keystroke writes the draft store from
  `onChange` and renders nothing. Changes that do not come from typing are written into the element
  by a store subscription: sending clears it, a command or restored message fills it, a paste folds
  into a chip, another window changes it. A refused paste puts the draft back, which a controlled
  textarea used to do by itself.
- **The pane renders from a view of the draft** (`composerDraftView`): its attachments, the command
  query (the text only while it can open the `/` or `@` list), the send block, and the size once
  past 90% of the ceiling. Ordinary typing changes none of it. Handlers read the current draft
  through `draftRef`.
- **The placeholder is there only while the draft is empty.**
- `src/renderer/src/panes/use-composer-draft.test.ts` pins these:
  - the view stays the same while text is typed;
  - the command query matches the command list's own rule;
  - the pane has no `value=` on a textarea and uses `useComposerTextSync`;
  - the placeholder rule holds.

Tried and not kept:
- `contain: paint` or `will-change: transform` on the textarea, and removing the composer's
  shadows: within noise.
- A fixed-height, strictly contained textarea: it halves per-key layout (1.04 to 0.70 ms at 4x) and
  saves about 0.3 ms of task per key. But it would need a JS auto-size to replace
  `field-sizing: content` and would fight the user's vertical resize.
- Hiding the tab strip, sidebar, timeline or telemetry: no single region carries the per-frame cost.

Per key in the 10k conversation at 11 tabs, from the probe:

| | task / key | script / key | style / key | React commits / 300 keys |
| --- | --- | --- | --- | --- |
| pane isolated, controlled textarea | 19.6–25.5 | 4.9–6.6 | 0.33–0.40 | 325–332 |
| uncontrolled textarea | 12.6–17.2 | 1.6–2.2 | 0.26–0.37 | 26 |
| + placeholder only while empty (final) | 12.3–13.1 | 1.5–1.6 | 0.09–0.10 | 26 |
| bare textarea over the full app | 9.4–11.1 | 0.8–1.0 | 0 | 25 |

### Behaviour checks (parked smokes, candidate build)

These passed:
- `smoke-pasted-text`: a refused paste keeps the draft, the chip unfolds, the paste is sent as an
  attachment.
- `smoke-steering`, run from a scratch copy whose launcher selector takes `.first()`: submit,
  pending delivery across reload, Escape keeping the unsent draft, restoring a message to the
  composer.

These failed, at the same step on HEAD 2804a8e, so the failures are not from this change:
- `smoke-steering` as committed: two launcher buttons match "Claude".
- `smoke-composer-drafts`: the file picker's results in a detached window. Every draft step before
  it passed: reload, close and reopen, split, "Open as window" showing the draft.
- `smoke-composer-backlog`: `/ed` leaves the mode on Auto instead of Edit. `/at` and `/pla` passed:
  the command list opens and inserts, and the composer clears.
- `smoke-browser-composer-button`: line 64, before the composer.

## 2. Typing while test instances run

The fix itself shipped earlier (de10b49, 3329115, b4dbb52; docs/perf/typing-under-load.md):
- test work and parked instances run below normal priority, including a parked instance's GPU
  process;
- vitest uses half the logical cores;
- `git.ship`, `app.update`, `run_and_summarize` and llama-server start below normal.

This round adds what was missing: the guard now checks the item's own case, a parked instance
starting, with a tight bound, and was run against a control.

### The guard

`perf-input --assert` holds a `launch` load (`electron-vite build` into `out/`, then a parked
Conductor launched from it, up for 8 s) to `--launch-bound-ms`, default 8 ms. The median p95 and the
median p99 over three rounds must each be within that of the same-run quiet median. The `swarm`
load keeps its 25 ms bound (`--bound-ms`). The documented command now runs both:

```
node scripts/smoke-lock.mjs --priority normal --timeout-min 60 -- node scripts/perf-input.mjs --label=guard --load=launch,swarm --repeat=3 --throttle=4 --assert
```

The owner stand-in is the candidate build (section 1), typed into at 4x, at normal priority.

### Numbers

Input to next paint in ms, three rounds each. Before this round's runs a smoke-lock queue had
cleared, but other agents' normal-priority work kept the quiet windows at 11–32% machine CPU.

Guard, as test work starts now (`t29-guard.json`). perf-input passed its asserts and exited 0.
smoke-lock then returned 3, because its cleanup could not attribute one leftover `conhost.exe`.

| Load | p95 by round (median) | p99 by round (median) | max | keys over 100 ms | machine CPU |
| --- | --- | --- | --- | --- | --- |
| quiet | 16.0 / 17.3 / 15.6 (16.0) | 19.3 / 18.9 / 17.3 (18.9) | 102.3 / 20.2 / 19.3 | 1 / 0 / 0 | 29 / 32 / 30% |
| launch | 16.8 / 14.5 / 16.6 (**16.6**) | 19.7 / 17.3 / 18.7 (**18.7**) | 28.4 / 18.9 / 22.2 | 0 / 0 / 0 | 37 / 28 / 39% |
| swarm | 31.2 / 34.1 / 29.6 (31.2) | 41.3 / 55.2 / 43.1 (43.1) | 67.9 / 136.4 / 51.4 | 0 / 1 / 0 | 70 / 74 / 79% |

- A parked instance building and starting moves typing by p95 +0.6 ms and p99 −0.2 ms: **no p99
  regression**, inside the 8 ms bound.
- Its processes all ran below normal: `electron.exe` ×4 and `node.exe` below normal.
- The swarm costs p95 +15.2 ms and p99 +24.2 ms, just inside the 25 ms bound.

Control, the load started the way test work ran before the fix (`--load-priority=normal`,
`t29-guard-control.json`):

| Load | p95 by round (median) | p99 by round (median) | max | keys over 100 ms | machine CPU |
| --- | --- | --- | --- | --- | --- |
| quiet | 13.5 / 10.0 / 9.8 (10.0) | 16.2 / 11.8 / 12.1 (12.1) | 26.0 / 16.1 / 15.6 | 0 / 0 / 0 | 19 / 11 / 11% |
| launch | 13.4 / 11.6 / 12.0 (12.0) | 16.0 / 14.6 / 14.1 (14.6) | 18.3 / 20.9 / 16.5 | 0 / 0 / 0 | 28 / 18 / 18% |
| swarm | 53.3 / 31.0 / 29.3 (31.0) | 102.3 / 52.0 / 43.4 (52.0) | 200.5 / 100.5 / 82.6 | 9 / 1 / 0 | 66 / 62 / 64% |

- The guard fails the control: `median p99 52 ms > quiet 12.1 + 25 ms`.
- The swarm without the fix cost p99 +39.9 ms and 10 keys over 100 ms (worst 200.5 ms).
- Its processes ran at normal priority, and its parked instance's GPU process above normal.
- A single launch at normal priority stayed inside the launch bound (p99 +2.5 ms) on this quieter
  machine. That matches the first round of this item (docs/perf/typing-under-load.md): one smoke
  alone never lagged, and the owner's lag needed a saturated machine. So on its own, the launch
  bound catches a regression in the launch path rather than reproducing the original report.

### What remains

- **Test browsers raise their own GPU process.** The swarm's vitest tree held 9 `chrome.exe`
  processes at above normal, in the guard and in the control. They are Playwright Chromium GPU
  processes from the Production agent's audit-browser tests (`src/main/production/browser.ts`).
  Chromium raises its GPU process to above normal on Windows whatever its parent's priority, which
  is the same thing the parked Electron instance does.
  - Tried in a scratch probe: `--disable-gpu`, `--disable-software-rasterizer` and
    `--disable-features=GpuProcessHighPriorityWin` all leave it above normal.
  - Headless `SystemInfo.getProcessInfo` lists only the browser process.
  - Lowering it needs a process-tree lookup after launch, then `os.setPriority`, as
    `src/main/background-priority.ts` does for Electron. That belongs in `browser.ts`, which has
    another agent's work in progress; handed to the controller.
- **A saturating swarm still costs about +15 ms p95 and +24 ms p99 at 4x** on a busy machine
  (+6 ms p99 on a calm one in the first round). That comes from below-normal threads sharing
  physical cores with the owner's renderer. It is inside the guard's bound.
