## Findings for the next batch

1. **Roster: add the two loop roles (REOPEN).** Add an *Architect* (codex gpt-6-astra, high: the contract, failing
   tests, acceptance and allowedPaths; alternate opus[1m]; brief `.conductor/loops/batch-delivery.md`). Add a *Code
   reviewer* (claude opus[1m], high, fresh tab: reviews the git diff once, limited to allowedPaths; alternate Astra;
   brief the batch-delivery review step). Test: R1b in `scripts/smoke-verify-vr8d-roster.mjs`, which reads the loop
   step roles from `.conductor/loops/*.md`.
2. **Approval reviewer on Ask: no review churn from the roster, but a trap elsewhere.** A roster Start opens it through
   the owner's scope, with no controller link (R3, with a live control). `approval-review-routing.ts` `enabled()` needs
   a controller, so its requests are never sent to a review: every Bash call waits for the owner's click instead.
   The churn case is a wizard opening this role with `tabs.open`, as docs/swarm/roster.md's table invites. The tab
   would then be a coworker, it is not marked `approval-reviewer:` (R3: null), and each of its tool calls would cost
   a fresh Opus review, which is the "No Ask mode under a wizard" pattern. Suggest either marking a roster-started or
   wizard-opened Approval reviewer as a reviewer, or running it read-only through plan mode rather than Ask. Check
   first whether the Claude CLI's plan mode fits the job.
3. Verifier runner: roster effort medium, while `docs/verification/verifier-brief.md` dispatches it at `effort:'low'`.
4. Cursor: the worst-case chain tail of about 2 s (finding above) is a design limit (`maxChainLinks: 4`,
   `chainWindowMs: 250`). If the owner wants the ~250 ms bound, a chain link would have to be a call the gesture's own
   call started (causality), not any call that starts soon after one settles.
