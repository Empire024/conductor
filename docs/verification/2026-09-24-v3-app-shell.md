## Failing scenarios for the next batch (write these as tests)

1. **19c298e4:** a stopped conversation's leftover queue must not count as running work.
   - Setup: a conversation that was interrupted mid-turn and still holds one queued prompt, with no turn running anywhere.
   - Expected: `confirmApplicationStop` returns 'stop' without a dialog, and `app.restart{force:false}` relaunches within a few seconds. Commit 4e04b8a claims exactly this ("a stopped conversation's leftover queue … is history, not work").
   - Actual: `hasRunningWork` counts it. The case to add to `close-confirmation.test.ts` is a projection with phase `interrupted` plus queued prompts whose runtime is still held. Also check what phase the stopped tab really has; the executor's tab is titled "Stopped with queued".
   - Related: `app.restart` replies `{restarting:true}` before that decision is made. A caller cannot tell that the restart is now waiting on a dialog. It should at least say "waiting for the owner" or return `pendingQuitConfirmation`.
2. **control-concurrent-requests:** a different mutation family must not queue behind another.
   - Setup: one credential with `git.ship({paths, waitSeconds:100})` in flight.
   - Expected: `tabs.open` from the same credential returns within about 1 s.
   - Actual: about 27 s. Keep the serialization per family and per target, for example two `tabs.rename` calls on one tab in arrival order.
   - One run of the concurrent-rename case also ended with the first title winning. Check the arrival order.
3. **e1610f01:** a restart right after steering must not freeze the reattached turn.
   - Setup: a runtime-host restart about 1 s after 5 `agents.steer` calls into a streaming Claude turn.
   - Expected: the turn continues past its cut-off word and completes, and the 5 prompts are answered in order.
   - Actual: output stops at the cut-off word, `waitingPrompts:6`, phase stays `running`.
   - Reproduce with `node scripts/smoke-lock.mjs -- node scripts/smoke-v3-s1-s2.mjs --queued`.

## New findings (not items of this group)

- **The shipped `scripts/smoke-local-restart.mjs` fails.** It failed 4 of 4 runs at `tabs.open` with "Workspace did not acknowledge the action", the 30 s timeout in `src/main/agent-control-ui.ts`. It calls `tabs.open` right after `projects.open`. The same call succeeds once the project's workspace is mounted (a reload and a click on the project row). An agent that opens a project and then a tab would hit the same race: `tabs.open` should wait for the workspace to mount instead of timing out. Evidence: `S7/summary.json`, `S7/concurrent-processes.txt`.
- **Rapid steering leaves a tab `running`.** With 5 `agents.steer` calls into a busy fixture Claude turn, all 5 were answered, but the tab's phase stayed `running` for more than 150 s (`S2/S2-control-summary.json`). This may be specific to the fixture; confirm it with a real Claude tab.
- **The debugging port stops answering after some restarts.** After a restart with a detached second window, the relaunched app's `--remote-debugging-port` never answered (4 of 4 runs). App control worked and both turns completed. It matters only to smokes, but it hides whether both windows were restored, which S5 therefore could not confirm (`S5/S5-summary.json`).
- **`scripts/smoke-lock.mjs` lets long smokes overlap.** It treats any holder older than 20 minutes as stale and lets the next waiter in, so during this run several smokes ran at once (V2's, a durable-jobs soak, and V3's). It should refresh the lock while the child lives, or check the holder's pid, instead of using the directory's age.
- **Process incident.** At about 2026-09-25T00:00Z the executor ran `taskkill /F /IM electron.exe /T` once. That killed 5 electron.exe test instances belonging to other agents. The owner's installed Conductor.exe was not touched. The incident is reported on the orchestration board (task_mug77088_0llif06) so that affected smokes are rerun.

## Not run, and what would unblock it

- **S16–S18** (22fc5f94 rollback, app-update-no-dialog-in-auto):
  - Rollback installs the downloaded NSIS package over the owner's installed app. A test profile cannot redirect that.
  - A running turn does make rollback wait on the "Work is still running" dialog, which S13 shows. But a slip in that guard would replace the owner's app, and the stronger guard was refused.
  - Options: the owner approves the installer-spawn guard for a test instance, or the rollback is tried once on a second machine or a Windows Sandbox.
  - The parts that are safe without any guard could run on their own: three builds from an Auto tab (S18), `restore-points.json` metadata and pinning. They were not split out in this batch.
- **Update-install variant of S1.** It restarts through `quitAndInstall` for the same reason, so it was not run; S1 covers the restart path.
